## Why this plan exists

Every comparable that takes its data seriously ships a download, and they all learned the same two lessons: the download is where the licensing story becomes real, and the version is where the citation becomes possible.

- **OpenHistoricalMap** treats reuse as a first-class feature: an Overpass API instance for targeted queries with GeoJSON export, daily full-database planet files on S3 (weekly with full revision history), and a REST API for raw OSM XML. The data is CC0 by default, and their own write-up stresses that "the downloaded data carries all source information along with it" — provenance travels with the rows, not in a separate document. Their wishlist is telling too: "easier downloads of data" and "automatic citation generation" are listed as things they still want.
- **Pleiades** (the ancient-places gazetteer) ships a downloads page, versioned dataset releases on GitHub (`pleiades.datasets`, `pleiades-geojson`), and a Wikidata crosswalk — the pattern of a stable place list with a machine-readable form that other projects build on.
- **World History Map** (omidhey/world-history-map) publishes a sources-and-licenses table with the dataset itself (borders GPL-3.0, Wikidata facts CC0, contributor summaries CC BY-SA 4.0) and archives every tagged release on Zenodo with a DOI (v1.0.0 is doi:10.5281/zenodo.23835597), so a citation can name a version whose files will never change.
- **historical-basemaps** (A. Ourednik) keeps it simpler and it works: one GeoJSON file per year, a `places.geojson` for settlements, and an auto-generated `index.json` listing year, filename, and countries per file so an application can pick a year without loading the whole set.
- **IndianaMap** (ArcGIS Hub) shows the filtered-download pattern: filter a dataset to a subset, then download the subset as Shapefile, CSV, or GeoJSON — the export follows the reader's selection, not just the whole database.
- **Frictionless Data Package** is the manifest standard the snapshot half of this plan copies: a `datapackage.json` descriptor naming the resources, their table schemas, and the dataset-level metadata (name, version, licenses, sources), published alongside the files — Zenodo-hosted packages are the reference implementation, and Zenodo's versioning rule is the one to copy: a new version is a completely new record with its own persistent identifier, linked to the old ones, so a citation of a specific version always resolves to the same files.

The map has the pieces and no export: plan 33 declares every adapter's license at the boundary, plan 37 versions published rows and tombstones the retired ones, plan 30's viewport + time-window query is exactly the "current view" a reader would want to export, and plan 43/44 own the rate limiting and the counting. What no plan owned is the extract itself — what formats, what rows, what license the file carries, how a reader cites it, and what happens when the data changes after they downloaded it. Without this plan, one of three things happens: a coding agent bolts a "download CSV" button onto the map that dumps the events table with no license, no version, and no provenance; or researchers scrape the map's API endpoints and get rate-limited by plan 43 for doing what the map should have offered; or the map stays a display-only object and the teachers and researchers who would have built on it go back to Wikidata SPARQL.

## The export model: two shapes, one manifest

### 1. Current-view export: download what you are looking at

- The map's export button (and the plan 38 detail page's "download this event" link) exports exactly the reader's current selection: the plan 30 viewport + time-window query, plus any active search filter and significance-band toggle (plan 46). IndianaMap's filtered-download pattern, applied to a map instead of a dataset gallery. The export is generated server-side from the same Postgres the map reads, using the same query — the file and the screen never disagree.
- Formats in v1: **GeoJSON** (canonical — geometry plus a `properties` object per event, the format QGIS, Leaflet, and OpenLayers all read) and **CSV** (flat — one row per event, latitude/longitude columns, the format a spreadsheet reader expects). No Shapefile in v1: GeoJSON imports into QGIS directly, and Shapefile's 10-character field-name limit would mangle the plan 32 date fields. No JSON-LD dump in v1: plan 38 already puts schema.org/Event JSON-LD on each detail page, and a whole-dataset JSON-LD file is a second serialization of the same rows for no reader.
- Caps and cost: a current-view export is capped at 10,000 events. Over the cap, the button points at the full snapshot instead of generating a bigger file. The endpoint is rate-limited per plan 43 (same per-endpoint limits as the map-data endpoints) and its responses are cached per query hash under plan 43's CDN rules — the same viewport exported twice is the same file. Download counts (not per-user tracking) go to plan 44's server-side event log, so the weekly review can see which views readers actually take with them.
- What travels with each row: the event's stable id and slug, title and display language (plan 47), the plan 32 EDTF string plus strict start/end bounds plus display string, coordinates, place name, significance band (plan 46), the source list with per-source license (plan 33 attribution union, per row), the Wikidata QID where one exists, the plan 49 relationship ids (causes/effects/sequence/part-of as id lists, not expanded rows — the reader joins them against the same file), and the image URL where plan 48 has one (a URL into the map's S3, not an embedded file — the export is data, not a media bundle).

### 2. Full snapshot: the versioned dataset

- Once a month, a scheduled job (not a per-request generation) writes the whole published set to the repo's S3 (the same bucket plan 48 uses for images) as an immutable snapshot: `historical-map-events-YYYY-MM-DD.geojson` and `.csv`, plus a `datapackage.json` manifest. The snapshot is never rewritten — a correction lands in the next snapshot, which is the plan 37 lifecycle rule applied to files: versions are append-only, and a citation of a snapshot always resolves to the same bytes.
- The manifest is a Frictionless Data Package descriptor: dataset name, version (snapshot date plus published-event count), `generated_at`, per-resource table schemas (field names, types, and the plan 32 / plan 46 / plan 47 field definitions), the license list with SPDX ids and links, per-source event counts, a sha256 checksum per file, and a ready-to-paste citation string ("History Map, snapshot 2026-11-01, 4,812 events from Wikidata (CC0) and Muffinlabs (CC BY-SA 4.0), https://…"). OHM's wishlist item — automatic citation generation — is a line in the manifest, not a feature to build later.
- The `/data` page lists the snapshots newest-first with event counts, license mix, and the citation string per snapshot, plus a `latest` pointer that always resolves to the newest snapshot. The page itself is a static page generated at snapshot time, not a live query — it cannot go stale, and it cannot hammer Postgres.
- Zenodo DOI is deferred, deliberately: World History Map's per-release DOI is the model, but it needs a Zenodo account, a manual deposit step, and a decision about whose name the deposit carries. The snapshot URL plus the immutable filename is citable today; the DOI is a backlog question, not a blocker. If James wants it, the deposit is one manual upload per snapshot, not a pipeline change.

### 3. The license of the file is the most restrictive license inside it

- Plan 33's rule — link-only stays link-only through fusion — extends to export: a Britannica link-only record exports as date + short factual identifier + link back, never text, exactly as it is stored. The export cannot launder a restriction the map itself respects.
- The export's own license is the most restrictive license among its rows, stated in the manifest and in a header comment in the CSV / a top-level `license` member in the GeoJSON. A snapshot that is all Wikidata CC0 is CC0. A snapshot with any Muffinlabs/Wikipedia-derived CC BY-SA text is CC BY-SA 4.0 for the file as a whole, with the per-row license fields letting a reader separate the CC0 rows if they want to. This is the CC BY-SA share-alike rule applied at file level: an adaptation (and a mixed export is one) carries the same license. CC BY-SA 4.0 also clarified database rights, which is what makes the file-level statement meaningful rather than decorative.
- Attribution travels in the file, not just on the page: every GeoJSON feature carries its source list and license; every CSV row carries source ids and license ids; the manifest carries the TASL attribution (title, author, source link, licence) for each source. A reader who forwards the file forwards the attribution with it — OHM's "the downloaded data carries all source information along with it" as a requirement, not an aspiration.
- What never exports: tombstoned rows (plan 37 — a tombstone is a removal, and the export is not a back door to deleted data), unpublished or review-queue rows (plan 34), reader suggestions and corrections (plans 39 and 53 — submitter prose and personal data never leave the review queue), saved collections (plan 52 — a reader's list is theirs, not dataset content), and merged-away rows (only the surviving canonical row exports, with the merge recorded in the plan 37 version history, not in the file).

## Surfaces

- **Map toolbar:** an Export button beside the search, opening a small panel: current view as GeoJSON or CSV, row count before download (so a 10,000-row cap is visible before the click, not after), and a link to `/data` for the full snapshot. The button is text-first, never a floating action button competing with pins.
- **Plan 38 detail page:** a "Download this event (GeoJSON)" link in the page footer, next to the Sources line — one event, one feature, same per-row fields as the full file.
- **Plan 40 semantic list and plan 42 bottom sheet:** the export panel is reachable from the list footer and the sheet's overflow menu, so the export is usable without a mouse and without seeing the map at all.
- **`/data` page:** the snapshot list, the citation strings, the license mix per snapshot, and a plain-language "how to cite this dataset" section. The page is generated at snapshot time and cached aggressively under plan 43.

## What this plan does not do

- No live query API in v1. The MCP server (plan 24) is the programmatic read surface; the export is files, not an endpoint to query. A public REST query API is a separate decision with its own rate-limit and abuse story (plan 43), not a side effect of a download button.
- No per-event media in the export. Images are S3 URLs in the properties (plan 48), not embedded files — embedding would balloon the snapshot and re-license images the export does not own.
- No export of the boundary layers (plan 51): OHM boundaries are OHM's data with their own download story (Overpass, planet files); the map's export is events, and the manifest says so.
- No real-time snapshot. The monthly cadence is a decision, not a limitation: a snapshot that regenerates on every publish is a file that changes under a citation. Staleness of up to a month is the price of citability, and the current-view export covers anyone who needs today's data.
- No accounts, no email-gated downloads, no download tracking beyond plan 44's aggregate counts. A dataset that demands sign-in is not an open dataset.

## Sequencing

- After plan 33 (the license declarations the export's per-row fields and file-level license are computed from), plan 37 (versions and tombstones define what a snapshot contains and what it never contains), and plan 30 (the viewport + time-window query the current-view export reuses).
- After plans 43 and 44 exist for the endpoint's rate limits and the download counting; the `/data` page and the snapshot job can land before them, since snapshots are static files on S3 behind the CDN.
- Before any public launch: the launch announcement can point researchers and teachers at `/data` instead of at an API they have to discover by scraping. The first snapshot lands with the plan 26 pilot's first published set, so the pilot's output is downloadable from day one.
- Not a plan 26 pilot blocker — the pilot validates ingestion from sources; the export is the pilot's output made portable.

## Done when

- The map's export panel downloads the current view as GeoJSON and CSV, with the row count shown before the click and the 10,000-row cap pointing at the snapshot instead of failing.
- The monthly snapshot job writes immutable GeoJSON + CSV + `datapackage.json` to S3, and `/data` lists them with counts, license mix, checksums, and citation strings.
- Every exported row carries its sources, licenses, QID, plan 32 date fields, plan 46 band, and plan 47 display language; Britannica link-only rows export as link-only; tombstoned, unpublished, and suggestion rows never appear in any export.
- The manifest validates against the Frictionless Data Package profile, and a downloaded snapshot re-validates against its own sha256.
- Plan 44 counts downloads by shape (current-view vs snapshot, GeoJSON vs CSV) with no per-user tracking, and plan 43's rate limits hold under a burst test against the export endpoint.
- No Splink anywhere in this plan (dedup remains Jev pairwise judging per the 2026-10-23 decision).
