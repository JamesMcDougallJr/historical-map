## Why this plan exists

A history map is a field tool pretending to be a website. The reader who opens it standing where something happened is the reader who most wants it to work, and that reader is the one most likely to have bad signal — a historic site, a museum, a rural battlefield, a plane. Today the map has no offline story at all: no service worker, no manifest, no tile cache, no cached event data (verified 2026-11-20: root `package.json` carries no Workbox, PWA, or PMTiles dependency, `app/` has no manifest, and there is no `public/` directory). The first version of this plan is deliberately small: make the app load, the last-viewed area render, and the last-viewed events show, with no network — and be honest about what is stale.

- **The acceptance test is one sentence, borrowed from Waypoints** (philipdamra.dev, an offline-first PWA for GPS waypoints): put the phone in airplane mode, kill the app, reopen it. The app loads. Your saved things are there. The map shows tiles for the area you were working in. If that sentence is true, the plan works; if any clause is false, it does not. Everything in this plan is in service of that test.
- **Workbox is the boring, correct tool for the service worker.** The MapVX tile-caching guide shows the shape: `CacheFirst` for map tiles (PBF files, capped — their example 10,000 entries / 7 days), `StaleWhileRevalidate` for other map assets, `NetworkFirst` for API calls. Waypoints does the same with one runtime cache — `CacheFirst` on the tile host, 1,500 entries / 30 days — plus a precached app shell (JS, CSS, HTML, fonts as `woff2`, fingerprinted so a changed chunk re-downloads and an unchanged one never does) and a `NavigationRoute` bound to the precached `index.html` so a hard refresh on `/map` while offline serves the shell and lets the router take it from there. This plan copies that shape, not a bespoke worker.
- **The PMTiles trap is the one thing that must not be re-learned the hard way.** Sailing Naturali's offline tide app (engineering.sailingnaturali.com) precached a 4.78 MB `.pmtiles` archive and the map drew on the first visit and never again: Workbox's precache stores and replays a full `200 OK`, the Cache API refuses to store a partial response, and `pmtiles` reads the archive with HTTP Range requests and requires `206 Partial Content` — a precached 200 is a hard error. The fix is a runtime-caching route with `rangeRequests: true` plus one non-ranged warm fetch, because a ranged request can never populate that cache on its own. If the map ever ships a PMTiles basemap, the archive goes in runtime caching, never in `globPatterns`. This is a hard rule in this plan, not a footnote.
- **Tiles and data are two different caches, and both are needed.** The Cache API holds tiles and assets; IndexedDB holds structured data — the last-viewed event windows (plan 30's viewport + time-window query results), the reader's device-local collections (plan 52, already offline by design), and the plan 38 detail pages the reader opened. Microsoft's PWA docs make the split explicit: IndexedDB is the best option for significant amounts of structured data because it does not block the main thread and is usable from both the app and the service worker; the Cache API is for network resources. The offline map needs both, or it shows a basemap with no events on it — a map with nothing to say.
- **Offline is a reader feature, not a sync product.** Nothing in v1 writes back while offline and reconciles later. Corrections (plan 39) and suggestions (plan 53) made with no network are not queued in v1 — the forms say so plainly and refuse, rather than silently eating the reader's work. Whether to queue them is question 83; the default is no, because a queue is a second product (outbox, retry, conflict, proof of delivery) hiding inside a caching plan.
- **The tile licence question is load-bearing, not legal trivia.** OpenStreetMap's tile usage policy discourages bulk downloading and heavy use of the donated tile servers; caching OSM tiles aggressively from tile.openstreetmap.org is borrowing someone else's generosity. The offline pack must come from a source whose terms allow it — a self-hosted PMTiles archive built from OSM data, or a paid tile provider whose plan permits caching — and plan 51's OHM boundary tiles (CC0/ODbL) are in the same position. Question 82 asks James to pick; the plan does not ship an offline pack from a source that forbids it.

## The offline pack: what is cached, and how

### 1. The app shell: precache everything the app is made of

- The service worker precaches the built app shell — JS, CSS, HTML, fonts, icons — on first visit, exactly the Waypoints shape: `globPatterns` over the built assets, fingerprinted filenames so a changed chunk gets a new URL and an unchanged one is never re-downloaded. The manifest (`app/manifest.ts` in Next.js App Router form, or `public/manifest.json`) makes the app installable: name, icons, theme colour, `start_url` `/map`, display standalone. The service worker must return 200 for the `start_url` while offline, or the app cannot launch offline at all — that is the PWA installability bar, and it is a done-when check, not an aspiration.
- The shell is the only thing precached. Tiles, event data, and images are runtime-cached on use (section 2) or explicitly downloaded (section 3). Nothing large rides in the precache, and the PMTiles archive never does — see the trap above.

### 2. Tiles and event data: runtime caching with honest caps

- **Basemap tiles** (the modern basemap, and the plan 51 OHM boundary overlay for the viewed period): `CacheFirst` with an `ExpirationPlugin` cap. The cap is a product decision with a number on it, and the plan's starting point is Waypoints' 1,500 entries / 30 days — enough for a city and its surroundings at the zooms a reader actually uses, small enough to fit a phone. The cap is measured against the real tile size in the build, not assumed; if the measured pack for a metro area at z0–14 exceeds the cap, the cap moves, not the honesty. The reader sees the cache size and a "clear offline data" control; storage is estimated with `navigator.storage.estimate()` and the pack never silently fills the device.
- **Event data:** the results of plan 30's viewport + time-window query are stored in IndexedDB as fetched, keyed by the query (viewport bbox + time window + filters), with the fetch time attached. Offline, the map serves the most recent cached window that covers the current viewport and says so: a visible, non-modal "showing saved events from [date/time]" banner, with a manual refresh when the network returns. A stale indicator is mandatory — an offline map that presents old events as current is lying, and the lie is worse than the gap. Plan 40's debounced aria-live summary announces the offline state; it is not colour alone.
- **Detail pages and images:** a plan 38 detail page the reader opened is cached (HTML + its plan 48 hero image) so it reopens offline. Images are cached at the thumbnail size the map actually shows, not the full Commons original — the offline pack is for reading, not archiving.
- **What is never cached for offline:** search (plan 19–24) — a semantic search needs the server, and an offline search box that returns nothing is worse than one that says "search needs a connection"; live data of any kind; and anything the reader has not viewed. The offline map is a record of what the reader already looked at, plus what they explicitly downloaded (section 3).

### 3. Explicit downloads: "save this area" as the deliberate offline act

- Runtime caching only covers ground the reader has already visited. The deliberate act is a "save this area" control on the map: the reader draws or accepts the current viewport, picks a zoom range, and the app downloads the basemap tiles, the plan 51 boundary tiles for the current cursor date, and the events in the current time window, into the same caches, with a progress indicator and a size estimate before the download starts. A saved area shows in a small list with its size and a delete control. This is the Sugandh offline-maps blueprint's step 2 ("predefine areas to cache") made into a button, and it is the only way the offline map covers ground the reader has never panned across.
- A saved area is bounded: one metro area at the zooms the reader uses, not a country, not the world. The size estimate is shown before the download, and the download refuses if it would exceed the cap or the device's remaining quota. The cap from section 2 applies to the sum of runtime cache plus saved areas, not to each separately — otherwise the "cap" is fiction.
- Saved collections (plan 52) are the natural companion: a collection's events are downloadable as a unit — "save this collection offline" downloads the events and their detail pages — because a reader who curated a set is the reader most likely to want it on a walk. The collection itself is already device-local in v1; this adds its event rows and images.

### 4. Offline behaviour of every surface: degrade, never pretend

- **Map:** renders from the tile cache and the IndexedDB event windows; pins the reader can tap open their cached detail pages; plan 50 playback works over cached events only and pauses at the edge of the cached window with the same "saved events" banner. The timeline (plan 30) scrubs only over cached windows and says so.
- **Today (plan 56):** `/today` renders from the cached day set if the reader opened it while online; otherwise it shows the cached set with its date labelled, or an honest empty state if no day set was ever cached. The RSS feed is not available offline and does not pretend to be.
- **Embeds (plan 55):** the embed route is a plain page; if the embedding site is loaded offline, the embed shows the same cached behaviour as the map. No separate embed offline work.
- **Corrections and suggestions (plans 39, 53):** the forms are disabled offline with a plain message ("you're offline — corrections need a connection") and the reader's draft is kept in the form so it survives reconnecting. No silent queue in v1 (question 83).
- **Analytics (plan 44):** offline use is invisible to JS tags, so it is counted server-side when the reader comes back: the service worker logs cache hits by surface in IndexedDB and the app reports the aggregate (counts only, no event contents) on the next online visit. No per-reader tracking beyond plan 44's aggregate posture.

## What this plan does not do

- No background sync, no outbox, no conflict resolution in v1: offline is read-only plus explicit downloads. Anything that writes — corrections, suggestions, collections created offline beyond the device-local v1 behaviour — is a separate plan.
- No push notifications in v1: push needs a service worker and a permission prompt, and the daily-habit notification is plan 56's question 79 territory, not this plan's. The service worker here serves content, not messages.
- No native app, no wrapper: the PWA is the mobile story, alongside plan 42's mobile map experience. If James ever wants an App Store listing, that is a packaging plan, not a caching plan.
- No tile server of the map's own in v1: the offline pack is cached from the existing tile source (or a PMTiles archive). Running a tile server is infrastructure, and plan 43 already owns the read-surface side of that decision.
- No curated-seed special case: the offline cache holds published rows only. Before the plan 26 pilot's first published set, there is nothing worth caching, and the 44 curated events do not become an offline demo set (same rule as plans 55 and 56).
- No Splink anywhere in this plan (dedup remains Jev pairwise judging per the 2026-10-23 decision).

## Sequencing

- After plans 30 (the query whose results are cached), 42 (the mobile reader is the offline reader), 43 (caching and rate-limiting are the same conversation — the offline pack must not trip the read-surface limits on download), and 51 (boundary tiles are part of the pack). After plan 52's device-local collections, which the offline pack extends.
- After the plan 26 pilot's first published set: an offline cache of the curated seed is a demo, not a feature, and the download button must not become the thing that keeps the 44 alive.
- Before any public launch: "works on the walk" is a launch-day claim, and the launch post can only make it if the acceptance test passes on a real phone in airplane mode.
- Not a plan 26 pilot blocker — the pilot validates ingestion; offline is the pilot's output made usable with no signal, the same way plan 54 is the output made portable as a file and plan 55 is the output made portable as an embed.

## Done when

- Airplane-mode acceptance test passes on a real phone: kill the app, reopen it with no network, the app loads, saved collections are there, the map shows tiles and events for the last-viewed area, and the stale banner shows the cache time.
- The app is installable (manifest + service worker returning 200 for the start URL offline); the install prompt is offered, never forced.
- A "save this area" download works end to end with a size estimate shown first, a progress indicator, and a saved-area list with sizes and delete controls; the combined cache respects its cap and the reader can clear it.
- The PMTiles rule is enforced in code review: no `.pmtiles` in precache `globPatterns`; any PMTiles route uses runtime caching with `rangeRequests: true` plus a warm fetch.
- Offline, the map, today view, and detail pages degrade honestly: cached content labelled with its time, uncached surfaces showing a plain "needs a connection" state, never a silent empty map or a stale-as-current lie.
- The tile source for the offline pack is one whose terms allow caching, recorded in the plan 33 licence declarations.
- No service-worker regression in the mocked e2e suite, and the e2e-real gate (plan 35) covers the offline acceptance test once it is green.
